# ADR 0009 — LLM 타임라인 워크로드 인코딩 (카탈로그 인덱스 재사용 패턴)

- 상태: 승인 (Phase L1, 2026-07-19)
- 관련: ADR-0002(타임라인 state 인코딩), 계약 TV-C1 v3.0 §6 (db-schema.md)

## 컨텍스트

GPU/LLM 화면(시안 llm_dashboard.pptx)의 타임라인은 GPU별로 어떤 LLM/AI 워크로드가
실행 중인지 간트로 보여준다. 막대 라벨은 워크로드 표기("vLLM (Llama-3.1-70B)",
"trainer.py" 등 7~8종)이고 색은 **분류 6종**(vLLM 추론/학습/데이터 처리/RAG/
TensorRT-LLM/기타)이다. Prometheus 메트릭으로 라벨 문자열을 직접 나르면 카디널리티와
소비 측 매핑이 복잡해진다.

## 결정

ADR-0002의 인코딩을 그대로 미러한다: `llm_gpu_timeline_state{env,node,gpu}` 게이지
값으로 **0=Idle, 1~8=워크로드 카탈로그 인덱스**를 노출하고, 카탈로그(인덱스 → 표시
라벨·프로세스명·분류·연계 서비스/모델)는 **계약 문서의 일부**(db-schema.md §6.4)로
고정한다. 소비 측은 값→라벨·색을 정적으로 매핑한다(Grafana value mapping,
React `LLM_CATALOG`).

- 슬롯은 **(node, gpu) GPU 단위**다 — 시안이 GPU 단위이고 MIG 필터가 없다.
  `mig` 라벨을 넣지 않으므로 기존 MIG 축 메트릭과 축이 다르다(v3.0 additive).
- GPU당 동시 1워크로드 — 타임라인 1행 1값 의미론(ADR-0002와 동일)을 유지한다.
- 분류 6색은 기존 쿼리 유형 6색 hex를 재사용한다(신규 색 토큰 없음 — design-tokens §1.5b).

## 대안

1. **워크로드 라벨을 메트릭 라벨로 노출** (`llm_gpu_timeline_state{workload="trainer.py"}`)
   — 기각: 시리즈가 (GPU × 워크로드)로 늘고, 간트 병합(연속 동일값)을 소비 측이
   라벨 문자열 비교로 해야 한다. 기존 인코딩 패턴과도 어긋난다.
2. **분류(6종)만 값으로 노출** — 기각: 시안 막대 라벨(모델명 포함)을 복원할 수 없다.
3. **프로세스 신원 캐리어(llm_process_running)의 range 조회로 타임라인 구성** — 기각:
   실행 중에만 존재하는 메트릭이라 과거 구간 복원이 retention·노출 규칙과 얽히고,
   ADR-0002가 이미 해결한 문제를 재발명하게 된다.

## 결과

- 타임라인 12시리즈 고정, range 쿼리로 과거 구간 복원 가능 — 기존 세그먼트화 로직
  (`web/src/lib/timeline.ts` `segmentTimeline`)을 카탈로그 주입만으로 재사용했다.
- 카탈로그 개정(워크로드 추가·이름 변경)은 **계약 개정**이다 — 값 인덱스가 계약의
  일부이므로 exporter·Grafana·web 3자 동시 갱신이 필요하다(§5.1 절차).
- 인덱스 1~4는 장수 서비스와 연계된다(홈 슬롯 고정) — 서비스 표(②)와 타임라인(③)이
  같은 카탈로그를 공유해 표기가 어긋날 수 없다.
